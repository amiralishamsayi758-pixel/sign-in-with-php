# مستند مسیرها و جریان احراز هویت

این سند رفتار واقعی نسخه فعلی پروژه را توضیح می‌دهد. پروژه یک **برنامه سنتی فرم‌محور PHP** است، نه یک REST API مبتنی بر JSON. واژه «مسیر» در این سند به فایل PHP قابل فراخوانی از مرورگر گفته می‌شود.

## 1. معرفی پروژه

این پروژه اطلاعات جیمیل، شماره موبایل و نام کاربری را دریافت می‌کند، یک کد تأیید چهاررقمی می‌سازد و پس از تأیید درست کد، یک توکن ورود ۲۴ساعته صادر می‌کند.

فناوری‌های فعلی:

- PHP ساده با `strict_types`
- MySQL و PDO برای ارتباط با پایگاه داده
- HTML و Tailwind CSS برای رابط کاربری
- JavaScript ساده برای اعتبارسنجی ظاهری، شمارنده و کادرهای کد
- PHP Session برای نگهداری وضعیت موقت و توکن‌های CSRF
- Cookie برای نگهداری توکن ورود

Laravel، Composer، JWT و هیچ چارچوب PHP دیگری استفاده نشده است. ارسال واقعی پیامک یا ایمیل نیز هنوز پیاده‌سازی نشده؛ بنابراین کد ساخته می‌شود و در پایگاه داده قرار می‌گیرد، اما به کاربر ارسال نمی‌شود.

## 2. جریان کلی احراز هویت

```text
ثبت جیمیل، تلفن و نام کاربری
→ اعتبارسنجی در process.php
→ ساخت کد چهاررقمی با اعتبار دو دقیقه
→ درج یا به‌روزرسانی رکورد users
→ ذخیره شماره در PHP Session
→ انتقال به verify.php
→ بررسی کد، CSRF و زمان انقضا در سرور
→ ساخت توکن تصادفی ۲۴ساعته
→ ذخیره هش توکن در MySQL
→ ذخیره توکن خام در Cookie از نوع HttpOnly
→ ورود به dashboard.php
→ تمدید کنترل‌شده اعتبار هنگام فعالیت معتبر
→ خروج با logout.php
```

جیمیل، تلفن و نام کاربری فقط **اطلاعات هویتی** هستند. تطبیق این سه مقدار به‌تنهایی باعث ورود یا تمدید توکن نمی‌شود. ورود فقط با کد معتبر یا کوکی توکن معتبر انجام می‌شود.

## 3. Base URL

آدرس پایه در محیط توسعه محلی:

```text
http://localhost:8000
```

نمونه کامل: `http://localhost:8000/process.php`

در محیط اصلی، دامنه متفاوت خواهد بود و باید از HTTPS استفاده شود.

## 4. روش‌های احراز هویت

| مفهوم | معنی و کاربرد واقعی |
|---|---|
| Verification code | کد چهاررقمی ساخته‌شده با `random_int(1000, 9999)`؛ دو دقیقه اعتبار دارد و برای اثبات دسترسی کاربر استفاده می‌شود. |
| PHP Session | فضای موقت سمت سرور؛ شماره در انتظار تأیید، پیام‌های یک‌بارمصرف و توکن‌های CSRF را نگه می‌دارد. |
| Authentication token | مقدار تصادفی ۶۴حرفی ساخته‌شده با `random_bytes(32)`؛ اجازه دسترسی به صفحه محافظت‌شده را می‌دهد. |
| Token hash | خروجی `SHA-256` توکن خام؛ فقط همین مقدار در MySQL ذخیره می‌شود. |
| HttpOnly cookie | کوکی `sign_in_auth` که توکن خام را نگه می‌دارد و JavaScript مرورگر نمی‌تواند آن را بخواند. |
| CSRF token | مقدار تصادفی موجود در Session و فرم؛ مانع ارسال درخواست حساس از یک سایت دیگر می‌شود. |

توکن CSRF، کد تأیید، توکن ورود و شناسه Session چهار مقدار مستقل با کاربردهای متفاوت هستند.

## 5. قالب درخواست و پاسخ

درخواست‌های فرم با قالب زیر ارسال می‌شوند:

```text
Content-Type: application/x-www-form-urlencoded
```

رفتار فعلی:

- صفحات با `GET`، سند HTML برمی‌گردانند.
- عملیات تغییر‌دهنده با `POST` انجام می‌شوند.
- نتیجه بیشتر عملیات یک پاسخ `303 See Other` و انتقال به صفحه دیگر است.
- خطاها به‌صورت پیام فارسی داخل HTML یا Flash Message در Session نمایش داده می‌شوند.
- کوکی Session و کوکی ورود باید بین درخواست‌ها حفظ شوند.
- هیچ مسیر JSON در نسخه فعلی وجود ندارد.

## 6. مستند مسیرهای فعلی

### 6.1 فرم ثبت اطلاعات

**File:** `index.php`  
**Method:** `GET`  
**URL:** `/index.php`  
**هدف:** نمایش فرم جیمیل، شماره موبایل و نام کاربری.  
**احراز هویت:** لازم نیست.  
**Session:** لازم نیست.  
**CSRF:** ندارد.

پارامتر اختیاری Query String:

| Field | مقدارهای پذیرفته‌شده | رفتار |
|---|---|---|
| `status` | `success` یا `database-error` | پیام سبز یا قرمز را نمایش می‌دهد؛ مقدار ناشناخته نادیده گرفته می‌شود. |

**پاسخ موفق:** HTML با وضعیت `200`. فرم به `/process.php` ارسال می‌شود.

**نکته واقعی:** پیام `status=success` در صفحه تعریف شده، اما جریان فعلی ثبت موفق به `verify.php` منتقل می‌شود و هیچ پردازشگر فعلی کاربر را به این وضعیت هدایت نمی‌کند.

### 6.2 پردازش ثبت اطلاعات

**File:** `process.php`  
**Method:** `POST`  
**URL:** `/process.php`  
**هدف:** اعتبارسنجی اطلاعات، ساخت کد و درج یا به‌روزرسانی کاربر.  
**احراز هویت:** لازم نیست.  
**Session:** پس از موفقیت ساخته یا ادامه داده می‌شود.  
**CSRF:** در نسخه فعلی ندارد.

فیلدهای درخواست:

| Field | Type | Required | Rules |
|---|---|---:|---|
| `gmail` | string | بله | قالب ایمیل معتبر و پایان با `@gmail.com`، بدون حساسیت به بزرگی حروف در پسوند |
| `phone` | string | بله | دقیقاً ۱۱ رقم ASCII با الگوی `09[0-9]{9}` |
| `username` | string | بله | بین ۵ تا ۱۰ کاراکتر بر اساس UTF-8 |

رفتار پایگاه داده در یک Transaction:

- شماره با `SELECT ... FOR UPDATE` جست‌وجو می‌شود.
- برای شماره جدید، رکورد با `resend_count=0` و `is_verified=0` درج می‌شود.
- برای شماره موجود، جیمیل، نام کاربری، کد و انقضا جایگزین و `resend_count` یک واحد زیاد می‌شود.
- `created_at` در به‌روزرسانی تغییر نمی‌کند.
- وضعیت تأیید و توکن ورود موجود فقط با تطبیق اطلاعات هویتی تغییر نمی‌کنند.
- اگر شمارنده به ۵ رسیده باشد، کد تازه ذخیره نمی‌شود و پیام محدودیت ثبت می‌شود.

**موفقیت:** شماره در Session ذخیره و پاسخ `303` به `/verify.php` داده می‌شود.  
**اعتبارسنجی ناموفق:** همان `index.php` با وضعیت `422` و پیام کنار فیلد نمایش داده می‌شود.  
**خطای پایگاه داده:** Rollback و پاسخ `303` به `/index.php?status=database-error`.  
**روش غیر از POST:** پاسخ `303` به `/index.php`.

امنیت موجود: اعتبارسنجی سمت سرور، Prepared Statement، Transaction، کد تصادفی امن و عدم نمایش کد.

### 6.3 صفحه تأیید کد

**File:** `verify.php`  
**Method:** `GET`  
**URL:** `/verify.php`  
**هدف:** نمایش چهار کادر کد، شمارنده و فرم ارسال مجدد.  
**احراز هویت:** توکن ورود لازم نیست.  
**Session:** کلید `verification_phone` لازم است.  
**CSRF:** یک توکن ساخته و داخل هر دو فرم قرار داده می‌شود.

این صفحه با Prepared Statement مقدارهای `code_expires_at` و `resend_count` را می‌خواند. زمان باقی‌مانده در PHP و با UTC محاسبه می‌شود و فقط تعداد ثانیه‌های باقی‌مانده به JavaScript می‌رسد. تازه‌سازی صفحه شمارنده را از ۱۲۰ شروع نمی‌کند.

**موفقیت:** HTML با وضعیت `200`.  
**Session نامعتبر یا کاربر حذف‌شده:** پاسخ `303` به `/index.php`.  
**خطای پایگاه داده:** صفحه با وضعیت `200` و پیام عمومی خطا نمایش داده می‌شود.

قبل از انقضا دکمه تأیید فعال و ارسال مجدد غیرفعال است. بعد از انقضا، وضعیت رابط برعکس می‌شود. امنیت به این دکمه‌ها وابسته نیست و سرور دوباره زمان را بررسی می‌کند.

### 6.4 پردازش تأیید کد

**File:** `verify-process.php`  
**Method:** `POST`  
**URL:** `/verify-process.php`  
**هدف:** بررسی کد و صدور توکن ورود.  
**احراز هویت:** هنوز لازم نیست.  
**Session:** `verification_phone` الزامی است.  
**CSRF:** الزامی و با `hash_equals()` بررسی می‌شود.

| Field | Type | Required | Rules |
|---|---|---:|---|
| `verification_code` | string | بله | دقیقاً ۴ رقم ASCII |
| `csrf_token` | string | بله | باید با توکن Session برابر باشد |

مراحل موفق در یک Transaction:

1. کاربر با شماره موجود در Session و `SELECT ... FOR UPDATE` خوانده می‌شود.
2. انقضا با ساعت UTC سرور بررسی می‌شود.
3. کد ورودی با مقدار ذخیره‌شده و `hash_equals()` مقایسه می‌شود.
4. توکن خام تصادفی ساخته و هش `SHA-256` آن ذخیره می‌شود.
5. `is_verified=1` و `resend_count=0` می‌شوند.
6. انقضای توکن و `last_authenticated_at` ثبت می‌شوند.
7. شناسه Session بازسازی و وضعیت تأیید موقت پاک می‌شود.
8. توکن خام فقط در کوکی `sign_in_auth` قرار می‌گیرد.
9. پاسخ `303` به `/dashboard.php` داده می‌شود.

**خطاها:** CSRF نامعتبر، قالب نامعتبر، کد اشتباه، کد منقضی، کاربر پیدا‌نشده یا خطای پایگاه داده؛ همه با پیام عمومی و انتقال امن مدیریت می‌شوند. کد یا توکن در پیام نشان داده نمی‌شود.

### 6.5 ارسال مجدد کد

**File:** `resend-code.php`  
**Method:** `POST`  
**URL:** `/resend-code.php`  
**هدف:** جایگزینی کد منقضی با کد تازه.  
**احراز هویت:** توکن ورود لازم نیست.  
**Session:** `verification_phone` الزامی است.  
**CSRF:** الزامی است.

| Field | Type | Required | Rules |
|---|---|---:|---|
| `csrf_token` | string | بله | تطبیق امن با توکن Session |

ارسال مجدد فقط وقتی مجاز است که کد فعلی منقضی شده و `resend_count < 5` باشد. بررسی فقط در رابط نیست و در PHP داخل Transaction انجام می‌شود.

**موفقیت:** کد قبلی جایگزین، انقضا دو دقیقه جلو برده، شمارنده یک واحد زیاد و `updated_at` تازه می‌شود؛ سپس پاسخ `303` به `/verify.php`.  
**ارسال زودهنگام یا رسیدن به محدودیت:** پایگاه داده تغییر نمی‌کند و با Flash Message به `/verify.php` منتقل می‌شود.  
**روش غیر از POST:** پاسخ `303` به `/verify.php`.

### 6.6 صفحه محافظت‌شده کاربر

**File:** `dashboard.php`  
**Method:** `GET`  
**URL:** `/dashboard.php`  
**هدف:** نمایش اطلاعات کاربر تأییدشده.  
**احراز هویت:** کوکی معتبر `sign_in_auth` الزامی است.  
**Session:** برای پیام موقت و CSRF خروج استفاده می‌شود.  
**CSRF:** برای خود GET لازم نیست؛ توکن فرم خروج در صفحه ساخته می‌شود.

تابع داخلی `authenticatedUser()` در `auth/check-auth.php`:

- توکن خام را از کوکی می‌خواند و قالب ۶۴حرفی Hex را بررسی می‌کند.
- هش توکن را می‌سازد و کاربر را با Prepared Statement پیدا می‌کند.
- `is_verified=1` و معتبر بودن `token_expires_at` را بررسی می‌کند.
- توکن نامعتبر یا منقضی را رد و کوکی را پاک می‌کند.
- اگر حداقل یک ساعت از `last_authenticated_at` گذشته باشد، اعتبار همان توکن را تا ۲۴ ساعت بعد تمدید می‌کند.

**توکن معتبر:** HTML با وضعیت `200`.  
**توکن غایب، جعلی یا منقضی:** پاسخ `303` به `/index.php`.  
**خطای پایگاه داده:** پاسخ `303` به `/index.php?status=database-error`.

`auth/check-auth.php` یک Helper داخلی است و API یا صفحه مستقل محسوب نمی‌شود.

### 6.7 خروج امن

**File:** `logout.php`  
**Method:** `POST`  
**URL:** `/logout.php`  
**هدف:** باطل کردن توکن و پایان Session.  
**احراز هویت:** کوکی ورود معتبر لازم است.  
**Session:** لازم است.  
**CSRF:** الزامی است.

| Field | Type | Required | Rules |
|---|---|---:|---|
| `csrf_token` | string | بله | باید با `auth_csrf_token` موجود در Session برابر باشد |

**موفقیت:** `auth_token_hash`، `token_expires_at` و `last_authenticated_at` برابر `NULL` می‌شوند؛ کوکی ورود و کوکی Session منقضی، Session نابود و پاسخ `303` به `/index.php` داده می‌شود.  
**CSRF نامعتبر:** توکن باطل نمی‌شود و پاسخ `303` به `/dashboard.php` برمی‌گردد.  
**روش غیر از POST:** پاسخ `303` به `/dashboard.php`.

### 6.8 آزمایش اتصال پایگاه داده

**File:** `test-db.php`  
**Method:** محدودیت روش ندارد؛ معمولاً `GET`  
**URL:** `/test-db.php`  
**هدف:** آزمایش ساده اتصال PDO.  
**احراز هویت، Session و CSRF:** ندارد.

اتصال موفق متن ساده و وضعیت `200` می‌دهد. شکست اتصال متن عمومی و وضعیت `500` می‌دهد. جزئیات PDO نمایش داده نمی‌شود. بهتر است این فایل در محیط اصلی عمومی نباشد.

## 7. قوانین اعتبارسنجی

| بخش | قوانین سمت سرور |
|---|---|
| Gmail | اجباری؛ عبور از `FILTER_VALIDATE_EMAIL`؛ پایان با `@gmail.com` |
| Phone | اجباری؛ فقط رقم ASCII؛ دقیقاً ۱۱ رقم؛ شروع با `09` |
| Username | اجباری؛ طول UTF-8 حداقل ۵ و حداکثر ۱۰ کاراکتر |
| Verification code | رشته دقیقاً چهاررقمی؛ کد ذخیره‌شده برابر باشد؛ زمان سرور قبل از انقضا باشد |
| Resend | Session و CSRF معتبر؛ کد فعلی منقضی؛ شمارنده کمتر از ۵ |
| Authentication token | ۶۴ کاراکتر Hex؛ هش موجود در جدول؛ کاربر تأییدشده؛ زمان انقضا در آینده |
| CSRF | رشته ارسالی و مقدار Session با `hash_equals()` برابر باشند |

اعتبارسنجی JavaScript فقط برای تجربه کاربری است. تصمیم نهایی همیشه در PHP گرفته می‌شود.

## 8. فیلدهای جدول users

| Field | MySQL type | Null/Default | کاربرد | حساسیت |
|---|---|---|---|---|
| `id` | `BIGINT UNSIGNED` | NOT NULL، خودکار | شناسه اصلی | عادی |
| `gmail` | `VARCHAR(254)` | NOT NULL | جیمیل کاربر | اطلاعات شخصی |
| `phone` | `CHAR(11)` | NOT NULL، UNIQUE | شناسه یکتای کاربر | اطلاعات شخصی |
| `username` | `VARCHAR(10)` | NOT NULL | نام نمایشی/کاربری | اطلاعات کاربری |
| `verification_code` | `CHAR(4)` | NOT NULL | کد تأیید جاری | بسیار حساس و کوتاه‌عمر |
| `code_expires_at` | `DATETIME` | NOT NULL | پایان اعتبار کد بر اساس UTC | امنیتی |
| `resend_count` | `SMALLINT UNSIGNED` | NOT NULL، پیش‌فرض ۰ | تعداد جایگزینی کد | امنیتی |
| `is_verified` | `TINYINT UNSIGNED` | NOT NULL، پیش‌فرض ۰ | وضعیت تأیید حساب؛ فقط ۰ یا ۱ | امنیتی |
| `auth_token_hash` | `CHAR(64)` ASCII | NULL، UNIQUE | هش SHA-256 توکن ورود | بسیار حساس؛ توکن خام نیست |
| `token_expires_at` | `DATETIME` | NULL | پایان اعتبار ورود | امنیتی |
| `last_authenticated_at` | `DATETIME` | NULL | کنترل فاصله تمدید توکن | امنیتی |
| `created_at` | `TIMESTAMP` | زمان ایجاد | زمان ساخت رکورد | عادی |
| `updated_at` | `TIMESTAMP` | به‌روزرسانی خودکار | آخرین تغییر رکورد | عادی |

جدول از InnoDB و `utf8mb4_unicode_ci` استفاده می‌کند. شماره تلفن یکتا است و روی انقضای کد شاخص وجود دارد. هش توکن با `ascii_bin` و شاخص یکتا نگهداری می‌شود.

## 9. پیام‌های وضعیت و خطا

- «اطلاعات با موفقیت ثبت شد و کد تأیید جدید ایجاد شد.»؛ در `index.php` تعریف شده ولی جریان فعلی آن را تولید نمی‌کند.
- «در ثبت اطلاعات مشکلی رخ داد. لطفاً دوباره تلاش کنید.»
- «وارد کردن آدرس جیمیل الزامی است.»
- «یک آدرس معتبر با پسوند @gmail.com وارد کنید.»
- «شماره موبایل باید دقیقاً ۱۱ رقم و با 09 شروع شود.»
- «نام کاربری باید حداقل ۵ و حداکثر ۱۰ کاراکتر داشته باشد.»
- «درخواست نامعتبر است. لطفاً دوباره تلاش کنید.»
- «کد تأیید باید دقیقاً چهار رقم باشد.»

خطاهای خام SQL، رمز MySQL، Stack Trace، کد تأیید و توکن خام در پاسخ‌ها نمایش داده نمی‌شوند.

## 10. کدهای وضعیت HTTP

| Status | استفاده واقعی |
|---|---|
| `200 OK` | نمایش صفحات HTML و موفقیت `test-db.php` |
| `303 See Other` | تقریباً همه انتقال‌های پس از POST و انتقال کاربر فاقد Session یا توکن |
| `422 Unprocessable Content` | نامعتبر بودن جیمیل، تلفن یا نام کاربری در `process.php` |
| `500 Internal Server Error` | فقط شکست اتصال در `test-db.php` |

نسخه فعلی برای روش نامعتبر `405`، برای نبود ورود `401`، برای CSRF نامعتبر `403` و برای محدودیت `429` برنمی‌گرداند؛ این حالت‌ها با `303` و پیام HTML مدیریت می‌شوند.

## 11. رفتار Session و Cookie

### کلیدهای Session

| Key | محتوا | زمان استفاده |
|---|---|---|
| `verification_phone` | شماره در انتظار تأیید | پس از `process.php` تا تأیید موفق |
| `verification_csrf_token` | توکن CSRF تأیید و ارسال مجدد | در `verify.php` و پردازشگرها |
| `verification_flash` | نوع و متن پیام یک‌بارمصرف | خطا/موفقیت صفحه تأیید |
| `auth_csrf_token` | توکن CSRF خروج | در Dashboard و Logout |
| `auth_flash` | پیام یک‌بارمصرف ورود یا خروج | در Dashboard |

اطلاعات کامل کاربر یا توکن خام ورود در Session ذخیره نمی‌شود.

Session با نام `sign_in_system_session` ساخته می‌شود. کوکی آن:

- تا بسته‌شدن مرورگر معتبر است (`lifetime=0`).
- `HttpOnly=true` دارد.
- `SameSite=Lax` دارد.
- در HTTPS دارای `Secure=true` و در HTTP محلی دارای `Secure=false` است.
- پس از ثبت اطلاعات و پس از تأیید موفق، شناسه Session با `session_regenerate_id(true)` عوض می‌شود.

کوکی ورود `sign_in_auth`:

- توکن خام را نگه می‌دارد؛ هش آن در MySQL است.
- ۲۴ ساعت اعتبار اولیه دارد.
- `Path=/`، `HttpOnly=true` و `SameSite=Lax` دارد.
- فقط روی HTTPS با ویژگی `Secure=true` ساخته می‌شود.
- با فعالیت معتبر، فقط وقتی حداقل یک ساعت گذشته باشد تا ۲۴ ساعت بعد تمدید می‌شود.
- توکن منقضی یا نامعتبر تمدید نمی‌شود.

## 12. بازبینی امنیتی

### ✅ پیاده‌سازی‌شده

- Prepared Statement برای همه ورودی‌های پایگاه داده
- Transaction و `SELECT ... FOR UPDATE` در جریان‌های حساس
- اعتبارسنجی سمت سرور
- ساخت امن کد با `random_int()`
- انقضای دو دقیقه‌ای و بررسی مجدد در PHP
- محدودیت پنج‌بار ارسال مجدد
- CSRF برای تأیید کد، ارسال مجدد و خروج
- ساخت توکن با `random_bytes()` و ذخیره فقط هش
- کوکی `HttpOnly` و `SameSite=Lax`
- بررسی انقضای توکن و تمدید کنترل‌شده
- چرخش توکن پس از تأیید دوباره کد
- بازسازی شناسه Session پس از مراحل مهم
- استفاده هماهنگ از UTC
- پنهان‌سازی خطاهای فنی و داده‌های حساس
- Escape کردن داده‌های نمایشی با `htmlspecialchars()`

### ⚠️ نیازمند بهبود

- فرم اولیه `/process.php` هنوز CSRF ندارد.
- روش HTTP نامعتبر و CSRF نامعتبر کدهای دقیق `405` و `403` نمی‌دهند و Redirect می‌شوند.
- محدودیت ارسال بر اساس رکورد است؛ Rate Limit مبتنی بر IP، بازه زمانی یا دستگاه وجود ندارد.
- فایل `test-db.php` بهتر است در محیط اصلی حذف یا از دسترسی عمومی خارج شود.
- وابستگی‌های Tailwind، فونت و تصویر از CDN دریافت می‌شوند و سیاست CSP تعریف نشده است.
- رمز اتصال دارای مقدار جایگزین داخل فایل تنظیمات است؛ محیط اصلی باید فقط از متغیر محیطی یا Secret Manager استفاده کند.

### ❌ موجود نیست

- ارسال واقعی کد با SMS یا Email
- محدودیت تعداد تلاش برای واردکردن کد اشتباه و جلوگیری کامل از Brute Force
- گزارش امنیتی و Audit Log برای ورود، خروج و تلاش‌های ناموفق
- سامانه بازیابی حساب یا تغییر امن شماره
- اجبار HTTPS در سطح وب‌سرور محیط اصلی
- REST API یا پاسخ JSON

## 13. نمونه جریان درخواست و پاسخ

### ثبت اطلاعات

```http
POST /process.php
Content-Type: application/x-www-form-urlencoded

gmail=test.user@gmail.com&phone=09123456789&username=parham
```

نتیجه معتبر:

```http
HTTP/1.1 303 See Other
Location: verify.php
```

نتیجه اعتبارسنجی ناموفق، HTML فرم را با وضعیت `422` برمی‌گرداند.

### تأیید کد

```http
POST /verify-process.php
Content-Type: application/x-www-form-urlencoded
Cookie: sign_in_system_session=...

verification_code=1234&csrf_token=...
```

اعداد بالا فقط نمونه‌اند و داده واقعی نیستند. کد صحیح و معتبر باعث `303` به `dashboard.php` و ایجاد کوکی `sign_in_auth` می‌شود. کد اشتباه یا منقضی با Flash Message به `verify.php` برمی‌گردد.

### ارسال مجدد

```http
POST /resend-code.php
Content-Type: application/x-www-form-urlencoded
Cookie: sign_in_system_session=...

csrf_token=...
```

اگر کد منقضی شده و محدودیت تمام نشده باشد، کد جایگزین و پاسخ `303` به `verify.php` داده می‌شود.

### خروج

```http
POST /logout.php
Content-Type: application/x-www-form-urlencoded
Cookie: sign_in_system_session=...; sign_in_auth=...

csrf_token=...
```

در موفقیت، توکن سمت پایگاه داده و کوکی‌ها پاک و کاربر به `index.php` منتقل می‌شود.

## 14. راهنمای آزمایش

### مرورگر

1. سرور را با `php -S localhost:8000` اجرا کنید.
2. `http://localhost:8000/index.php` را باز کنید.
3. با داده معتبر و نامعتبر، پیام‌های هر فیلد را بررسی کنید.
4. در Developer Tools بخش Network، پاسخ‌های `303`، `422` و مسیر انتقال را ببینید.
5. در Application/Cookies بررسی کنید که `sign_in_auth` دارای `HttpOnly` است. مقدار آن را نمایش یا منتشر نکنید.
6. تازه‌سازی `verify.php` نباید شمارنده را دوباره روی `02:00` قرار دهد.

### MySQL Workbench

از جدول `users` فقط وضعیت‌های لازم مانند `resend_count`، `is_verified` و زمان‌های انقضا را بررسی کنید. کد تأیید و هش توکن را در تصویر، گزارش یا پیام منتشر نکنید.

### Postman

Body را روی `x-www-form-urlencoded` بگذارید. نگهداری Cookie را فعال کنید. برای مسیرهای محافظت‌شده باید ابتدا HTML صفحه را دریافت و توکن CSRF همان Session را از فرم بردارید. پاسخ‌ها JSON نیستند و Redirect و HTML دریافت می‌شود.

## 15. پیشنهاد برای تبدیل به REST API در آینده

> **پیشنهادی و هنوز پیاده‌سازی نشده**

این مسیرها در پروژه فعلی وجود ندارند و فقط طرح احتمالی آینده هستند:

| Method و URL پیشنهادی | هدف | نمونه پاسخ JSON پیشنهادی |
|---|---|---|
| `POST /api/register` | اعتبارسنجی اطلاعات و شروع تأیید | `{ "status": "verification_required" }` |
| `POST /api/verify-code` | بررسی کد و ایجاد نشست ورود مناسب API | `{ "status": "verified" }` |
| `POST /api/resend-code` | ساخت کد تازه پس از انقضا | `{ "status": "code_replaced" }` |
| `GET /api/me` | دریافت اطلاعات کاربر واردشده | `{ "id": 1, "username": "example" }` |
| `POST /api/logout` | باطل‌کردن توکن | `{ "status": "logged_out" }` |

در طراحی آینده باید نوع کلاینت، سیاست Cookie یا Header، CORS، CSRF، Rate Limit، کدهای HTTP و قالب ثابت خطاها جداگانه تصمیم‌گیری شوند. این پیشنهاد نباید با مسیرهای فرم‌محور فعلی مخلوط شود.

## جمع‌بندی وضعیت فعلی

- پروژه فعلی فرم‌محور و مبتنی بر HTML، Session، Cookie و Redirect است.
- تمام عملیات حساس سمت سرور دوباره بررسی می‌شوند.
- هیچ JSON API فعالی وجود ندارد.
- بخش REST فقط پیشنهاد آینده است.
- `status=success` در `index.php` تعریف شده ولی در جریان فعلی استفاده نمی‌شود.
- نبود CSRF در فرم اولیه و نبود محدودیت تلاش کد اشتباه، مهم‌ترین شکاف‌های فعلی هستند.
